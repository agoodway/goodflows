# Design

## Context

See proposal.md for why this exists. Today `Options.log_dir` is the workflow log directory (`--log-dir` plus `path_component` for a named workflow, or `--log-dir` itself for legacy top-level jobs). `run_job` creates `<index>-<name>[.pNN].stdout.log` and `.stderr.log` with `File::create`, so the next run truncates them. `duration_ms` starts when `run_job` starts. The scheduler in `runner::execute` is the only place that knows a job was waiting on dependencies or on a free slot. `summary` is built in `src/main.rs` after reporting and rendered by `src/output/report.rs`. Settings already merge shared, workflow, and profile values; CLI overrides for parallelism and fail-fast are arguments to `Settings::resolve`, called from the per-workflow path and the aggregate `list`/`validate` path in `src/main.rs`. Commands are spawned with `tokio::process::Command` (`kill_on_drop`, `process_group(0)`) and reaped through tokio `Child::wait`. `libc` is a Unix-only dependency and is already used without a cfg guard, so Windows is not a supported target. Reporting already creates a `workflow_run_id` UUID. There is no hash crate and no date crate.

## Goals / Non-Goals

**Goals:** One run id shared by the log directory and the history file. Prune by filename so mtime and git checkout do not choose the victim. Publish optimizer fields from the same structs the history file serializes. Measure CPU per command and peak RSS with one run-wide sampler that scans `/proc` once per sample for every running command, sooner when output is flowing and on a slow poll when it is not.

**Non-Goals:** See proposal.md. Also out of scope: editing the user's `.gitignore` or `.gitattributes`, restoring the old flat log paths, and hashing environment values.

## Decisions

### One run identity, lexical names

Create one lowercase v4 UUID and one UTC timestamp, truncated to a second, at the start of a run. The UUID is also the reporting `workflow_run_id` when reporting is configured, so an invocation has one run id. Format the timestamp from `SystemTime::now()` since `UNIX_EPOCH` with a small, unit-tested days-to-civil helper rather than a new crate (for example 2026-11-04T00:00:00Z → `20261104T000000Z`); `started_at` is the same instant in RFC 3339. Two runs in the same second sort by their random UUID, so their relative prune order is arbitrary. Format the directory and file stem as `YYYYMMDDTHHMMSSZ-<uuid>`. Logs go in `<effective log dir>/<stem>/`. History goes in `<history dir>/<path_component(workflow)>/<stem>.json`, and legacy top-level jobs use the workflow name `default` only for history. Log placement otherwise stays as it is today, so a legacy config does not gain a `default/` log subdirectory.

Prune compares those names as strings. Never delete the stem just created, even if the clock steps backward and an older name sorts newer. Never delete a name that does not match the stem pattern, and never follow or unlink a symlink. Create the log run directory before jobs; if that fails, the run fails as it does today. Each run creates it as `.<stem>.tmp` (a name prune never matches), takes an exclusive `flock` on `.goodflows.lock` inside it, and only then renames it to `<stem>`; the lock follows the open file across the rename and is held until exit, so no prune ever sees a stem-named directory that is not yet locked. A crash between create and rename can leave a `.<stem>.tmp` directory, which prune keeps like any unrelated name. Create the log base, staging, and run directories with mode 0700 (the run directory keeps the staging directory's mode across the rename), the lock file with mode 0600, and each log file with `create_new`, mode 0600, and `O_NOFOLLOW`, so retained logs are private and a planted entry at a log path fails that instance instead of being followed or truncated. Prune logs immediately after that, skipping any directory whose lock cannot be taken with `LOCK_NB`; only a missing lock file means an unlocked (old or crashed) run, and a lock file that exists but cannot be opened skips that directory and is reported as a prune warning, so a concurrent run sharing `--log-dir` never loses its live directory and a crash loop still stays within the cap. Both prunes treat an entry that is already gone (`NotFound` while listing, reading its type or size, or removing it) as pruned, since two runs pruning the same directory race for the same victims. Each prune applies the caps of the run doing it to every matching entry in the directory, whichever profile produced it; a profile that wants its own retention needs its own `--log-dir` or `history_dir`. Snapshot the signal state once when the summary fields are finalized; that snapshot drives the outcome in the history file, `summary`, the report header, and the exit code, in text and JSON mode alike. Write and prune history after that snapshot and before the summary is emitted, so `history_file` is present only when the write succeeded; a prune failure after a successful write is reported but keeps `history_file`, since the file exists. History is written exactly when a summary is emitted, including cancelled runs; a run that errors before a summary (for example `runner::execute` returning `Err`) writes none. History and log prune errors are reported on stderr and do not change the exit code.

Alternatives considered: pruning by mtime is wrong after `git checkout`. One rewritten `history.jsonl` conflicts on every branch and rewrites bytes git already stored. A timestamp alone collides when two runs start in the same second.

### Settings and flags use the existing precedence

Add `history: bool` (default false), `history_dir: Option<PathBuf>`, `log_runs`, `history_runs`, and `history_bytes` to `Settings`, `SettingsOverrides`, and `EffectiveSettings`. Extend `Settings::resolve` with a CLI-overrides struct carrying the history and retention flags and update both call sites. Profile and workflow overrides use `Option<bool>` for `history` so an explicit `false` wins over a lower `true`. Resolve directories the way workdir and `spool_dir` already do: config `history_dir` (shared, workflow, and profile) is joined to the config file's directory inside `Config::load`, and the default `goodflows-history` resolves the same way; `--history-dir` and `--log-dir` resolve from the invocation directory. `list` and `validate` therefore show the resolved path, as they already do for `workdir`.

CLI: `--history`, `--no-history` (they conflict), `--history-dir`, `--log-runs`, `--history-runs`, `--history-bytes`. `--no-history` forces off. Otherwise `--history` or `--history-dir` forces on. Otherwise the resolved setting applies. Numeric flags override the resolved setting. The flags are global like `--parallelism`, so `list` and `validate` serialize the resolved values with CLI overrides applied; they never write history. `reports upload` rejects all six flags alongside its existing run-only flag list. Reject 0 for the three caps at config validation, and at parse time with `value_parser!(u64).range(1..)` (exit 2), the same pattern as `--budget`. Do not add an upper bound on `history_bytes`.

### Optimizer fields live on the result, not a side channel

Extend `JobResult` with `blocked_ms`, `queued_ms`, and `commands`, all `#[serde(skip)]` like `started`. One `Scheduling<'a>` struct in `runner` serializes `started`, `blocked_ms`, `queued_ms`, and `commands` (omitted when empty) from a result; `SummaryResult<'a>` flattens the `JobResult` and its `Scheduling` for each `summary.results` entry, and the history instance flattens the same `Scheduling`, so the extra fields are maintained in one place. Record command costs on a small struct the summary result and the history file both serialize: `kind` (`condition` for a job or step shell condition, `command` for a job or step command), optional `step`, `wall_ms`, and the optional CPU and RSS fields; `commands` is omitted when empty.

The history file does not serialize `JobResult`, because it carries `stdout_tail`, `stderr_tail`, and job and step `outputs`. It uses a separate history instance struct with an explicit allowlist: `name`, `partition`, `status`, `exit_code`, `command` (truncated), `error` (truncated and redacted), `duration_ms`, then the flattened `Scheduling` fields `started`, `blocked_ms`, `queued_ms`, `commands`. In `error`, wherever the per-run log directory begins a whole path anywhere in the string, it and anything below it (so no log filename survives) become `<log>`; then wherever the workdir begins a whole path, it becomes `<workdir>` and a path below it keeps its tail. A match must start the string or follow a non-path character and must end at `/`, the end, or a non-path character, so `/w` never matches inside `/w2/x` or `/x/w`. Configured command text is stored verbatim.

The record also carries run context so an agent does not compare unlike runs: `environment` (the `--env` profile, omitted without one), `requested_jobs` (`--jobs` as given, omitted when empty), and `source` with `commit` and, when known, `dirty`. Source comes from `reporting::source::capture`, run before `runner::execute` when history is enabled, reusing the reporting session's capture when report-producing jobs made it capture one; it never records the branch or remotes, and is omitted when there is no commit. These are additive, so `schema_version` stays 1. They are history-only: the summary already has `environment`.

The scheduler computes, once per scheduling pass, whether every dependency of each configured job passed; the ready scan and the launch loop share that vector, which stays valid through the pass because the only results recorded in between are skips, and a skip never makes a dependency pass. The scheduler records, per unit, measured from the start of `runner::execute`, when dependencies became satisfied (the moment the last dependency's result is recorded) and when the unit was launched, skipped, or cancelled. `blocked_ms` ends at dependency satisfaction or at an earlier skip or cancel. `queued_ms` is the time after that until `run_job` or until a later skip or cancel. `max_in_flight` is the high water mark of units inside `run_job`, kept by a counter each unit increments on entering `run_job` and decrements on leaving it, so a finished task the scheduler has not joined yet does not count.

`graph_sha256` is SHA-256 (new `sha2` dependency) of compact JSON, keys in this order, nulls explicit:

```json
{"jobs":[{"name":"","command":null,"depends_on":[],"partitions":null,"timeout_secs":null,"shell":true,"condition":null,"steps":[{"id":"","command":"","shell":null,"condition":null}]}]}
```

`partitions` is null or `{"count":N,"strategy":"index"}`. `condition` (job or step) is null, or `{"kind":"expression"|"shell","text":"..."}`; `Condition::LegacyShell` and `Condition::Shell` both hash as `shell`. The document covers the selected jobs after profile partition counts, not unselected jobs and not env values. Truncate history command and error strings to 1024 bytes on a char boundary. Leave the existing summary `command` and `error` strings alone so stdout JSON does not lose text.

Host is sampled once at run start, next to the run identity and before `runner::execute`, so memory reflects the machine the jobs started on. `os` and `arch` are `std::env::consts::OS` and `ARCH`. Host memory is Linux `/proc/meminfo` `MemTotal` and `MemAvailable`, in bytes, parsed by a pure `parse_meminfo`; omit both when that file cannot be read or either field is missing. `logical_cpus` comes from `std::thread::available_parallelism`, or 1 when that fails.

History `duration_ms` is `execute_ms`: from immediately before `runner::execute` until it returns. Reporting uploads after the last job are network time, not job time, so they stay in `summary.duration_ms` only; the summary gains `execute_ms` additively.

### CPU from `wait4`, RSS from a Linux process-group sample

On Unix, `wait4` the spawned pid and store `ru_utime` and `ru_stime` as whole milliseconds. That rusage includes descendants the child waited for, which is the command's CPU for `sh -c`. For a `timed_out` or `cancelled` command the group is killed before `sh` reaps its children, so CPU is a lower bound. macOS records CPU and omits `peak_rss_bytes` and the host memory fields.

#### Reaping on Unix

Tokio reaps a `tokio::process::Child` itself, so a second `wait4` on the same pid would race it (ECHILD, or a later kill of a reused pid). On Unix, goodflows owns the reap instead: spawn with `std::process::Command` plus `process_group(0)`, wrap the stdout and stderr fds as tokio pipe readers (`tokio::net::unix::pipe::Receiver::from_owned_fd`), and wait for the child on a dedicated, small-stack reaper thread per command that sends the result through a oneshot channel, using that receiver in the existing select. A blocked wait must not hold a thread of tokio's blocking pool: log writes (`tokio::fs`) and RSS scans use that pool, its size is bounded while `parallelism` is not, and a pool filled with reapers would stall the log writes that drain the pipes, so the children would never exit. Only if the thread cannot be spawned does the reaper fall back to `spawn_blocking`. On timeout or cancel, `killpg` the child's group (the child leads it, so this signals the child too). If the child has not been reaped yet, also `kill(pid)` in case it left its group. Both kills live in the drop guard created right after spawn, so an early return, a `?` path, or an aborted task still kills a child that left its group instead of leaving its reaper waiting forever. To keep that kill from reaching a reused pid, the reaper first waits with `waitid(P_PID, pid, WEXITED | WNOWAIT)`, which leaves the exited child a zombie, then reaps with `wait4` and marks it reaped under one lock; the late `kill(pid)` takes the same lock and is skipped once the flag is set. The blocking wait then returns. Build the exit status with `ExitStatusExt::from_raw`. Never call tokio `wait`, `try_wait`, or `kill` on that pid.

Peak RSS is Linux-only. The runner already puts the child in its own process group. While the command runs, sample the sum of resident memory for every `/proc` pid whose process group is that child, reading the `rss` field (field 24, in pages, times the page size) of `/proc/<pid>/stat`, which is the value `/proc/<pid>/status` reports as `VmRSS`; zombie (`Z`) and dead (`X`) processes and processes with 0 resident pages (caught starting or exiting) are skipped, so a recorded peak is never 0. One run-wide sampler task, started by `runner::execute`, owns the scanning: each command registers its group on spawn and takes its peak on exit (a guard unregisters it on any early return), and each scan reads `/proc` once on tokio's blocking pool, builds the sums for every registered group, and raises each group's peak. A stdout or stderr read only asks for a scan soon; the sampler honors that at most every 50ms and otherwise scans every 200ms while any group is registered, and registering a group asks for a first scan. Per-command scanning would cost one full `/proc` walk per running command per sample. A scan still running when a command exits may miss it. Omit `peak_rss_bytes` on other platforms rather than report the direct child's `ru_maxrss`, which misses grandchildren and uses different units. A quiet command still gets the 200ms poll. A command that exits before any live sample leaves only a zombie, so `peak_rss_bytes` is omitted when no sample saw a live process. Descendants that leave the group with `setsid` or `setpgid` are not counted.

Alternatives considered: `ru_maxrss` of the direct child is portable and wrong for `cargo` and `mix`. A cgroup would measure the group exactly and is not something this CLI can require. A per-second trace would blow the 10 MB budget.

### The history file is not pretty-printed

Serialize with `serde_json` compact encoding and one trailing LF. Create the history base directory with mode 0700 (any missing parent too), then open it with `O_DIRECTORY | O_NOFOLLOW`, `mkdirat` the workflow directory with mode 0700 and open it the same way, and do everything else relative to that descriptor: create `.tmp<random>` with `openat(O_CREAT | O_EXCL | O_NOFOLLOW, 0600)`, write and `fsync` it, `linkat` it to `<stem>.json` (which fails rather than replace an existing name), and `unlinkat` the temporary name; prune lists the directory through `fdopendir` and removes with `unlinkat`. A symlink at either directory fails the open (`ELOOP`, or `ENOTDIR` on some systems, both reported as a refused symlink), and swapping a component for a symlink after the open cannot redirect the write. A crash between create and link can leave a `.tmp<random>` file; prune removes a regular one older than an hour, leaving fresh ones that another run may still be writing. `schema_version` is the integer 1. Key order is the struct field order, but readers parse JSON rather than rely on it; git sees a new file per run, so later runs do not rewrite earlier bytes.

README documents committing `goodflows-history/`, gitignoring the log directory, and a `.gitattributes` line `goodflows-history/** text eol=lf linguist-generated`. It also says history files contain configured command text and must not be committed when commands inline secrets, recommends enabling history in a CI profile or with `--history` rather than shared `[settings]`, warns that a new untracked file trips clean-tree checks run after goodflows and that runs from different machines in one directory are not directly comparable, and gives a `.gitignore` line for keeping history local. The CLI does not write either file.

### Module layout

`src/retention.rs` is a leaf module holding `RunIdentity`, `is_stem`, `LogRun`, the lock helpers, and both prunes; it depends only on `src/fsutil.rs`, never on `runner`. `src/fsutil.rs` holds the filesystem helpers reporting and history share (`write_atomic`, `real_dir`, `dir_builder` for 0700 directories, `canonical_uuid`) and the descriptor-relative `Dir` used for history. `src/history.rs` builds records and depends on `runner` for results; `runner` depends on neither.

## Risks / Trade-offs

- [Log paths move under a per-run directory] → Basenames stay the same. README calls out the break. No compatibility flag; `log_runs = 1` still uses a new directory.
- [RSS samples can miss a spike between polls, and can miss processes that exit before a sample] → The poll is 200ms and also runs on output. The field is a peak of samples, not a cgroup peak.
- [CPU and RSS can disagree about grandchildren] → CPU includes descendants the child reaped. RSS sums the group only while they are alive to be sampled.
- [The checkout cap does not shrink `.git`] → README says so. Prune only drops files from the next commit's tree.
- [Clock stepped backward] → The active stem is never pruned by the run that created it.
- [History write fails] → The run's exit code is unchanged and `history_file` is absent, so a full disk does not fail the checks. A prune failure after the write keeps `history_file`.
- [Committed history leaks command text] → Files hold configured command text up to 1 KiB per job, never env values or output. README tells users not to commit history when commands inline secrets and to enable it per profile or per run.
- [Thousands of concurrent commands] → Each running command holds one small reaper thread rather than a blocking-pool thread, so the pool stays free for log writes and RSS scans.
- [Concurrent runs share `--log-dir`] → Live directories are locked and skipped by prune, so the cap can be exceeded until the overlapping run exits.

## Migration Plan

No stored data to migrate. The first `--log-dir` run after the change creates a new directory beside the old flat files; those old files are not matching stems, so prune leaves them. Users delete the old files by hand. Rollback is reverting the binary. History files from `schema_version` 1 stay valid if a later version adds fields only in new files.
