# Tasks

## 1. Partition configuration and validation

- [x] 1.1 Add `partitions` to `Job` in `src/config.rs`, accepting an integer or a `{ count, strategy }` table (strategy `index` only, unknown keys rejected with specific messages rather than serde's generic untagged-enum error), normalized and serialized as `{ count, strategy }`; verify with unit tests for integer, table, default strategy, `strategy = "timings"`, unknown key and non-integer values in `cargo test --locked`.
- [x] 1.2 Validate counts in 1..=64. Reject `outputs` mappings on partitioned jobs, `partitions` together with `reports`, and `needs.<partitioned>.outputs.*` references in conditions and output mappings. Reject `GOODFLOWS_PARTITION`/`GOODFLOWS_PARTITION_COUNT` in job and step `env` through a separate constant (not `config::RESERVED_ENV`, which drives reporting scrubbing), generalize the reserved-variable error text in `validate_env`, and make `validate_credential_env_names` reject `url_env`/`token_env` naming either variable. Thread the partitioned-job set from `validate_jobs` through `validate_job`/`validate_condition` to `validate_expression`. Verify with inspection tests in `tests/inspection.rs` that each invalid config fails `goodflows validate` before execution, for both top-level jobs and named workflows, including `token_env = "GOODFLOWS_PARTITION"`.
- [x] 1.3 Show partition count/strategy in `list` text output and in the `jobs` JSON event (omitted for unpartitioned jobs), and leave `config_valid` unchanged with counts per configured job; verify with `tests/inspection.rs` cases for `list` text and `--json` output and a `validate` case reporting configured-job counts.
- [x] 1.4 Document the `partitions` field, accepted forms, 1..=64 range, reserved variables (including the `url_env`/`token_env` rule in the "Test timing reports" section), the no-outputs and no-reports rules, and the reserved future strategies in the README Configuration section; verify the documented example passes `goodflows validate` with the built CLI.

## 2. Scheduler expansion

- [x] 2.1 In `runner::execute`, expand jobs into ordered units (job index plus optional partition), track results/started state per unit, and resolve readiness and blocking per dependency job across all of its units (blocked only after all sibling units finish); verify with `tests/scheduling.rs` cases: all instances pass and the dependent runs, one instance fails and the dependent is skipped after siblings finish, an upstream failure skips every instance, and results are in unit order.
- [x] 2.2 Apply slot accounting, fail-fast and cancellation per unit; verify with `tests/scheduling.rs` cases for parallelism 4 with 3 instances leaving a free slot, parallelism 2 with 3 instances queuing the third, fail-fast skipping an unstarted sibling while a running sibling finishes, and a signal cancelling running and unstarted instances with the signal exit code preserved.
- [x] 2.3 Give each instance its own `timeout_secs` budget and failure tails; verify with a `tests/runner.rs` case where one instance times out and the others pass.

- [x] 3.2 Add a `JobExecution::command` flag that withholds `GOODFLOWS_OUTPUT` without condition semantics, use it for command-only partitioned jobs, and keep step output files and step-to-step outputs inside an instance; verify with `tests/steps.rs` cases for a command-only instance (variable absent, job outputs empty) and a two-step instance reading `steps.a.outputs.key`.
