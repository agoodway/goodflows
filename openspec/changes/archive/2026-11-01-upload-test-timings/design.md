# Design

## Context

See proposal.md. The CLI source is version 0.4.0; the currently installed executable is 0.3.0. `Config`, `Settings`, `Job` and named workflows use strict Serde validation. The scheduler returns job results and the main command emits a final summary. Commands already receive merged process/job/step environments, and JSON output is centralized in `Output` with schema_version 1. There is no HTTP dependency or reporting support.

## Goals / Non-Goals

**Goals:** Separate report capture from network delivery, retain replayable reports, keep invocation/job isolation, and preserve existing result semantics.

**Non-Goals:** Sending arbitrary artifacts/stdout, live event streaming, adding a success-dependent upload job, changing the scheduler, or calculating balanced partitions.

## Decisions

### D1. Opt-in configuration

Add a top-level optional reporting block shared across workflows; environment profiles continue to affect existing settings only. Individual jobs opt in with `reports = ["exunit-timings"]`. First release supports that single distinct format; duplicates/unknown formats are validation errors, as is a reports declaration without the reporting block. A reporting block with no selected reporting jobs performs no collection/network work.

```toml
[reporting]
project = "goodcases"
url_env = "GOODFLOWS_URL"
token_env = "GOODFLOWS_API_KEY"
spool_dir = ".goodflows-logs/reports"  # optional; overrides the .goodflows/reports default

[[jobs]]
name = "test"
command = "mix test.parallel"
reports = ["exunit-timings"]
```

Project is required and MUST match the server slug rule (1-64 bytes, `[a-z0-9][a-z0-9_-]*`). It is the path slug of an existing GoodFlows project owned by the API key's account and is never sent in the request body. The CLI does not create projects; url_env/token_env MUST be valid environment variable names; env names default to the names above; spool_dir defaults to `.goodflows/reports`. Resolve relative spool paths inside `Config::load` against the configuration file's directory (`base`, as for workdir), independent of child workdir, and carry the reporting block through the `Config` rebuilt by `Config::workflow`. Document adding the spool directory to the consuming project's `.gitignore`. Reject inline tokens and unknown config keys. `url_env` and `token_env` must differ and must not name `GOODFLOWS_RUN_ID`, `GOODFLOWS_REPORT_DIR` or `GOODFLOWS_OUTPUT` (one `config::validate_credential_env_names` serves config validation and replay). A job or step `env` entry for the configured `token_env` is a validation error naming the job, because the token is removed from every command and the value would otherwise vanish silently. `validate` and `list` expose only nonsecret config and never require network credentials. Use the existing job/workflow selection path; do not run unselected jobs to obtain reports.

### D2. Persistent invocation spool

Create a v4 UUID for a reporting invocation and always serialize it in lowercase canonical form, which the server requires. Under `<spool>/<uuid>/`, atomically write a manifest with project, workflow/environment, source context captured before creating the spool, configured credential env names, and job directory mappings. The spool, run and per-job `reports/`, `pending/` and `acks/` directories are created with mode 0700 before any job starts, so a job cannot pre-create a state directory as a symlink; every snapshot and acknowledgement write first checks with `symlink_metadata` that the job directory and the state directory are still real directories. Each manifest report entry stores only `report_id` and an `index`; `<job>/pending/NNN.json`, `<job>/acks/NNN.json` and `<job>/acks/NNN.rejected.json` are derived from the encoded job directory and that index, never stored as paths. Never persist endpoint/key values or arbitrary environment variables. Encode both workflow and job directory names with the reversible percent encoding in `config::workflow_log_component` (generalized/renamed to a path-component encoder) rather than the lossy, truncated job log stem in `runner.rs`. Validation rejects a reporting job whose name is longer than 64 UTF-8 bytes or contains control characters, which is the server's job-name rule. This also bounds the encoded directory name at 192 bytes.

Each selected report-producing job receives an absolute `GOODFLOWS_REPORT_DIR` pointing to `<run>/<encoded-job>/reports/` and `GOODFLOWS_RUN_ID` containing the UUID. Apply reserved values after job/step overrides; `validate_env` rejects `GOODFLOWS_RUN_ID` and `GOODFLOWS_REPORT_DIR` in every job/step `env` (all jobs, not only reporting jobs); existing `GOODFLOWS_OUTPUT` overwrite behavior is unchanged. Whenever a reporting block exists (whether or not a spool was created), both reserved names are removed from the expression env map and with `Command::env_remove` from every command, and only report-producing jobs of a created run then receive their own values, so a nested invocation never writes into an enclosing invocation's directories. The runner shares one `Arc<ReportingEnv>` across job tasks. Because child commands inherit the CLI process environment and `.envs()` only adds entries, removing the configured reporting token MUST use `Command::env_remove(<token_env>)` after `.envs(env)` in `JobExecution::command` for shell, non-shell, condition and step commands (as is already done for `GOODFLOWS_OUTPUT`), and the token MUST also be removed from the merged env map before expression evaluation so `${{ env.<token_env> }}` resolves to null and cannot leak into job outputs or events. The publisher retains its captured key only in its own process. Same-user processes are not a security boundary; as a mitigation, on Linux the CLI calls `prctl(PR_SET_DUMPABLE, 0)` once it has read a key (run and replay), so other same-user processes, including jobs, cannot read `/proc/<pid>/environ` or ptrace it. `execve` resets the flag, so jobs are unaffected.

Preserve the producer's suite run_id and report_id inside JSONL. The UUID is a separate `workflow_run_id` in uploaded envelopes, allowing multiple suites or repeated ExUnit executions within one job. Parallel producer workers inherit the same directory without any CLI dependency on Mix partition internals.

If the spool cannot be created, emit `reporting_skipped` with reason `spool_unavailable` and run checks without reporting env injection or historical-file fallback. This avoids turning delivery infrastructure into a check prerequisite. Persist job terminal results in the manifest before collecting when possible. A hard-killed CLI can leave an unfinished manifest/raw files; replay only accepts finalized immutable snapshots, and reports that have not been finalized are retained for diagnosis rather than guessed into a new request.

### D3. Collection after processes finish

After `runner::execute` returns and process groups have been cleaned up, collect direct regular `*.jsonl` files in each executed reporting job's isolated directory. Do not recursively glob the repo, follow symlinks, read default formatter history, or upload job logs. Skipped-before-execution jobs contribute no report. Missing/empty directories are explicit collection outcomes, not synthetic reports. If `runner::execute` returns an error (no summary path), mark the manifest aborted and do not collect. If a signal was received, still collect and freeze snapshots locally without starting any request, and report them as `report_upload_pending` with reason `cancelled`.

Read bounded UTF-8 JSONL in order. Enforce 256 reports and 256 MiB total source bytes per job, a 32 MiB encoded request maximum per report and 100,000 records. A source file over 33 MiB (the request limit plus a 1 MiB allowance for formatting differences) is rejected as `request_too_large` before it is read; lines are iterated lazily and parsing stops as soon as the exact compact size of the records exceeds 32 MiB. Collection runs in `spawn_blocking`. A signal that ended the jobs does not stop collection (above); a signal that arrives during collection stops it between reports, leaving the remaining files raw and counted as `collection_interrupted`. A final invalid JSON fragment is discarded and marks the envelope truncated; an invalid earlier record rejects that report. An unterminated but valid final JSON record is retained. Validate format marker, identity consistency and the shared field allowlist before serializing an envelope. Every server vocabulary and limit enforced locally (envelope keys, event fields, outcomes, filter tags, size and depth limits) lives in one module, `src/reporting/contract.rs`, whose `CONTRACT_VERSION` names the server change it was copied from and is sent in the User-Agent. The local allowlist is required to stop locally knowable rejections before a snapshot is frozen, which couples the CLI to the server: a report using vocabulary the server added later is rejected locally and never becomes replayable (only its raw JSONL is kept). Server contract changes must update that module and ship a CLI release before producers emit the new vocabulary. Rejected or oversized files remain untouched and produce structural codes only.

For each valid report, create a frozen request snapshot in the run's pending area by atomic replacement before attempting HTTP. Each envelope is frozen as soon as it is built, so collection holds at most one body; only `(report_id, index)` is kept for the duplicate check. Set envelope `suite_id` from the suite_started event `run_id`, copy `report_id`, `partition` and `partition_count` from suite_started, and set `truncated` from the collection outcome. Keep relative test file locations unchanged; they are relative to the test producer's working directory. Source context is only commit, branch and dirty, nullable when unavailable; capture with `git rev-parse HEAD`, `git symbolic-ref --short -q HEAD` and `git status --porcelain --untracked-files=no` run in the effective resolved `settings.workdir` with a 2-second total timeout (any failure or timeout yields null fields), and never store remote URLs. A commit that is not 40 or 64 hex characters, or a branch longer than 256 bytes, becomes null. Include selected workflow (the resolved workflow name, `default` for top-level jobs), environment (null when no profile is selected), job name and final job status from the captured invocation. Job status maps runner `Status` to `passed`, `failed`, `timed_out`, `cancelled` or `skipped`, and any result without a mapping becomes `unknown`. The envelope has exactly the server D1 top-level keys (`format`, `workflow_run_id`, `workflow`, `environment`, `job`, `job_status`, `source`, `report`) and never includes `project` or `account_id`. Before snapshotting, validate the D1 byte-length, U+0000, identifier and partition grammar rules. The server's identity key excludes `suite_id`, so `report_id` must be unique within a job across suites. If two collected reports in one job share a `report_id`, reject all of them with code `duplicate_report_id`, remove any snapshot already frozen for them, and leave the source files untouched rather than choosing one. Do not read current Git state during replay.

### D4. Shared HTTP contract

Use the authoritative wire contract at `../goodflows_web/openspec/changes/archive/2026-11-01-store-test-timings/design.md`, D1. The base URL is resolved from url_env and the private key from token_env. Append `/api/v1/projects/<project>/test-reports` to an origin-only URL, taking `<project>` from the manifest (already slug-validated, so no escaping is needed); reject userinfo, query strings, fragments and non-root base paths. Allow HTTPS and HTTP only for literal loopback hosts/localhost; do not follow redirects or forward auth to a new origin. Use `reqwest` 0.12 with `default-features = false` and rustls TLS on the ring provider (no OpenSSL/libssl dynamic dependency, no aws-lc build tooling in the Debian 12 release builder), trusting both the bundled WebPKI roots (`rustls-tls`) and the operating system's roots (`rustls-tls-native-roots`, via `rustls-native-certs`; on Linux its `openssl-probe` dependency only locates certificate files and links nothing), plus `uuid` 1 with `v4`/`serde`. TLS failures (a `rustls::Error` anywhere in the error chain, including inside nested `io::Error` payloads) are reported as `tls_error` and not retried. Because edition 2021 does not make the resolver MSRV-aware, `.cargo/config.toml` sets `[resolver] incompatible-rust-versions = "fallback"` so `cargo update` respects `rust-version`; verify with `cargo +1.88.0 check --locked` and the release packaging glibc check. Avoid shelling out to curl or parsing stderr for status.

Accept only 200/201 acknowledgements with a valid server UUID, matching report_id, valid status and duplicate flag. Treat 409 as an immutable conflict, not success. 400, 409, 413, 415 and 422 reject the frozen bytes themselves, so resending the same immutable snapshot can never succeed: record them in `<job>/acks/NNN.rejected.json` (`report_id`, `reason`, `http_status`), emit `report_upload_pending` with `terminal: true`, and let replay skip them. All other responses leave the snapshot pending. Retry transport errors, 429 and 5xx at most three attempts per report, with one- and two-second backoffs. A delta-seconds Retry-After replaces the backoff; when it is not shorter than the remaining budget the report is left pending immediately, because waiting could not lead to another attempt inside the budget. The HTTP-date form of Retry-After (and any unparsable value) falls back to the backoff schedule. Do not retry 3xx redirects or any 4xx other than 429 (including 400/401/403/404/406/409/413/415/422) automatically. A 404 means the project slug does not exist on the key's account; it leaves reports pending with code `project_not_found`. 503 (storage unavailable or the server's concurrent-read cap) is retried like other 5xx, honoring `Retry-After`.

Publishing is sequential after all job results, with one 30-second total budget, a 3-second connect limit and a per-request limit of 10 seconds plus 1 second per started MiB of body (42 seconds for a 32 MiB report), each clipped to remaining time; `reports upload --budget <seconds>` (1-3600) raises the budget for large reports on slow links. Immediately before sending, each snapshot (run or replay) is read without following symlinks, bounded to 32 MiB, re-validated against the full contract and compared with the manifest identity (run id, workflow, environment, job, job status, source, report id); a snapshot that fails is reported `invalid_snapshot` and not sent. The budget is checked before each snapshot is read so validation cannot run past it. Unattempted reports remain pending. Cancellation interrupts waits/requests immediately; no new request begins after a signal. Sanitized diagnostics contain status/code and local report identity, never raw response bodies, request records, URLs containing credentials or key values. No runtime credentials means local-only collection, an explicit skipped-delivery event and normal check exit status. A present but invalid origin (non-loopback HTTP, path, userinfo, query or fragment) is a delivery skip: emit `reporting_skipped` with reason `invalid_url`, send no request and keep the check exit status. 401/403 responses leave reports as `report_upload_pending` with a structural code. In replay, both cases exit nonzero.

### D5. Replay and acknowledgement state

Add `goodflows reports upload <run-directory>`. This command reads only a finalized local manifest and frozen snapshots; it does not require a project checkout or execute jobs. Everything in the run directory is treated as untrusted: the manifest version must equal the supported version (checked before the schema), and the manifest must pass the config rules (project slug, env names via `config::validate_credential_env_names`, lowercase canonical UUID, workflow/environment/job names of 1-64 bytes without control characters, unique job names) or replay refuses it. A job whose `dir` is not `path_component(name)` has all its reports counted invalid. `publish::endpoint` validates the slug itself as a last line of defense against `Url::join` normalization. Because the manifest selects which environment variables become the endpoint and key, only run directories from trusted invocations should be replayed. Resolve endpoint/key through the saved env-variable names; do not persist their values. Use the same contract, budget and validation rules as automatic publication. Preserve stored workflow/source/job metadata exactly.

Atomically mark each confirmed server acknowledgement in local state. Original JSONL and snapshots remain on disk after success; retry skips acknowledged reports. Concurrent retries can issue the same immutable request safely; state updates must merge by report identity rather than overwrite unrelated acknowledgements. If state update fails after a server commit, leave the request replayable and let server idempotency resolve it. Explicit replay exits 0 only when every collected valid report is acknowledged, none is recorded as rejected by the server and no collection errors remain; collection rejections therefore keep replay nonzero for that run (the spec scenario "Everything already acknowledged" is scoped to runs without collection rejections). Server-rejected reports are skipped with reason `rejected_by_server`; deleting the marker makes them replayable again. The summary reports `acknowledged`, `pending`, `rejected` and `invalid`. Signal exit codes take precedence. There is no automatic pruning policy in this change.

### D6. Output and scheduler boundary

Keep collection/publication in a new reporting module coordinated by main, rather than changing dependency success rules. Extend runner options only to supply per-job reporting environments. Job duration_ms remains command execution time; reporting time never becomes test time. Perform bounded publication before emitting the existing final workflow summary so summary remains the last event. Reporting events are best-effort: emit failures (for example a closed stdout) are ignored inside reporting, and the finalized manifest is written before any `reports_collected` event, so an output failure can neither leave a run unreplayable nor change the check exit status. Add opted-in `reports_collected`, `report_uploaded`, `report_upload_pending`, and `reporting_skipped` events, with run/job/report ids, counts and structural reason codes. Per-file rejections and missing/empty directories are carried as reason codes and counts in `reports_collected` rather than new event types. Each new event gets a text-mode render arm in `output::render`, which otherwise silently drops unknown events. Do not emit record contents.

Existing summaries still describe checks only and determine ordinary run exit status. A failed upload cannot turn a failed test green or a passing test red. Workflows without reporting retain their existing output shape. JSON events continue using the centralized schema_version field.

### D7. Alternatives

A GoodCases upload script is smaller locally but was rejected by the user's requirement that publishing live in Goodflows. HTTP calls in the formatter would contaminate test collection and couple producers to the destination. A dependent upload job would be skipped after test failures. Uploading every historical file cannot distinguish invocations. A single request containing all partitions increases retry size and loses independently acknowledged progress; per-report requests fit existing producer identities.

## Risks / Trade-offs

- [Spool growth] -> Keep data intentionally for replay, document manual removal after acknowledgement, and defer retention automation.
- [Hard CLI kill before snapshot finalization] -> Preserve raw files and manifest without claiming automatic recovery of unfinished metadata.
- [Concurrent execution overwrites unrelated logs] -> Reporting uses unique invocation directories even when ordinary log-dir behavior is unchanged.
- [Large source reports] -> Bound scanning/serialization and retain rejected files locally rather than silently truncating valid events.
- [Reporting env names previously used by commands] -> Document reserved names and reject explicit overrides; reporting credentials belong to the publisher.
- [Server vocabulary drift] -> The local allowlist lives in one versioned contract module; a mismatch rejects reports locally (raw files kept, not replayable), so server contract changes ship a CLI release first.
- [Same-user processes read the key] -> Not a boundary this change claims; Linux non-dumpable mode blocks `/proc/<pid>/environ` and ptrace from same-user processes.

## Migration Plan

Apply the server's `scope-recipes-by-project` change, then implement and deploy the companion web endpoint. Create the configured project on the account before enabling uploads. Release a CLI with config parsing and report publishing before adding reporting fields to GoodCases. Validate both existing and named workflows and environment profiles. Removing the reporting block and per-job reports declarations restores the previous workflow contract; pending local reports remain retryable with the supporting CLI. This artifact change does not install a binary or enable production upload.
