# Design

## Context

See proposal.md for motivation and scope. `src/main.rs` currently loads and resolves the entire config locally before invoking `runner::execute`. `Config::load` canonicalizes workdirs and reporting paths; those absolute paths cannot be sent to another machine. `Output` already renders versioned JSON events in human and machine formats. The runner starts a separate Unix process group for each command.

The companion's `docs/pool-protocol.md` supplies session REST endpoints, Phoenix Channels v2 authentication, once-per-session tar.gz upload, member readiness, one command per member, sequence-numbered byte output, replay, cancellation, and release/reset. It supplies no durable detached workflow service, arbitrary artifact download, or full durable output history. Its cancellation script kills the outer exec process group with SIGKILL; nested goodflows commands have their own groups. Member reset is therefore essential after interrupted workflows.

The decisions below complete implementation details not selected in conversation; they are proposed defaults for review. The confirmed choices are one member for the complete workflow, current local changes, and existing disconnect behavior.

## Goals / Non-Goals

**Goals:** Reuse the remote scheduler and existing pool contract; retain one shared filesystem for dependent jobs; make transport failure distinguishable from a failed check through a structural `error` event and the absence of a confirmed summary (both exit 1, matching the existing "runtime error" exit code); bound transfer memory and every cleanup attempt.

**Non-Goals:** Local scheduling of remote jobs, detached execution, Git checkout on the member, uploading the host binary, extending server limits, preserving arbitrary remote files after reset, or changing local-run behavior.

## Decisions

### 1. Use the existing pool session as a transport

Expose `--pool <slug>` and `--project <slug>` for explicit or implicit run only. Reject either on list, validate, init, and reports upload; reject `--project` without `--pool`. Project comes from `--project`, then the raw config's reporting project; absence is an actionable preflight error. Endpoint and private key come from `GOODFLOWS_URL` and `GOODFLOWS_API_KEY`, independently of optional reporting credential names. Validate pool/project slugs with the server's slug rule (`valid_project_slug` in `src/config.rs`). Validate `GOODFLOWS_URL` as an origin only by reusing the publisher's endpoint check (`src/reporting/publish.rs` `endpoint`: HTTPS or loopback HTTP, no userinfo, path, query, or fragment) and the same rustls/native-root TLS policy; refactor that check into a shared helper rather than duplicating it. Derive the socket URL by mapping `https`→`wss` and `http`→`ws` on `/api/v1/socket/websocket?vsn=2.0.0`; the subprotocol token uses the protocol's unpadded base64url encoding. Reject a missing key or a `pk_`-prefixed public key locally before any request. Disable redirects and never put credentials in URLs or diagnostics. The pool transport connects directly for both REST and WebSocket and ignores `HTTPS_PROXY`/`HTTP_PROXY` in this version so the two channels never diverge; document this, and leave proxy CONNECT support to a later change.

`--pool`/`--project` are declared `global = true` like the existing flags so both `goodflows run ci --pool x` and `goodflows --pool x` parse. Clap therefore also accepts them on list, validate, init, and reports upload; reject them explicitly in those branches of `src/main.rs` (extending the existing `reports upload` global-flag rejection and adding checks to the init/list/validate branches) with exit code 1, matching existing manual rejections.

Create a session with `max_members: 1`, `acquire_timeout_ms: 120000`, and a short workflow label. Use the documented Phoenix subprotocol token authentication, channel join/reply refs, and heartbeat. Join the session channel before starting the workspace upload and keep the socket/heartbeat task running concurrently with the HTTP PUT, so a long upload cannot exceed the server's unjoined-client disconnect grace. Upload once, wait for readiness, and submit exactly one workflow exec. Keep REST, channel state, and lifecycle handling in `src/remote/`, separate from the existing runner.

Alternatives considered: SSH bypasses the requested pools; distributing individual jobs introduces cross-member files and a second scheduler; a new durable server workflow API changes the agreed disconnect model. Running the installed CLI as one exec fits the selected approach.

### 2. Snapshot the actual Git working tree

Require a Git working tree in the first version. Discover its root from the invocation directory. Preserve the invocation directory as a relative remote cwd and discover the default config there using the existing filename order. Explicit config paths must resolve inside that root and be included in the upload; an ignored explicit config is an error with guidance to track it or change ignore rules. Never silently add ignored files.

Enumerate tracked entries with `git ls-files --cached --stage -z` (so gitlink mode 160000 is visible) and nonignored untracked files with `git ls-files --others --exclude-standard -z`, deduplicate paths, and read bytes from disk rather than the index or HEAD. Skip paths deleted locally; preserve executable modes. Tracked paths marked skip-worktree (sparse checkout) are not local deletions: fail before leasing with guidance rather than silently omitting them. Do not upload Git administrative metadata, including linked-worktree `.git` files. Support internal relative symlinks without dereferencing them (the archive builder must disable symlink following, e.g. `tar::Builder::follow_symlinks(false)`), rejecting absolute symlinks, links that escape the root, special files, and paths through symlinked ancestors; the server also rejects links resolving outside its workspace. Reject submodule gitlinks and untracked nested repositories (untracked directory entries containing their own `.git`) in this version rather than silently sending an incomplete checkout. Write deterministic tar headers (fixed uid/gid/owner names; modes limited to 0644/0755). Empty directories and ignored build outputs are not included.

Build a private temporary gzip tar outside the workspace. Check compressed size, expanded payload size, and entry count against the protocol defaults (256 MiB, 2 GiB, 100,000); stream compression and upload from disk. These are client guards, not a promise that a server has matching configured limits. Archive completion freezes this invocation's bytes; do not claim an atomic filesystem snapshot while editors are changing files. A detected file replacement or read error fails before leasing. Remove the temporary file on every terminal path.

Alternatives: `git archive HEAD` loses uncommitted work; archiving the entire directory includes ignored caches and local-only files.

### 3. Validate and resolve paths on the member

Branch into remote mode before `Config::load`. Parse enough raw TOML locally to discover config/project and optional reporting credential names, without resolving host workdirs or computing CPU count. Do not serialize the locally resolved config. The uploaded config is validated in full by the remote binary before jobs start. Relative workdirs and reporting spool paths resolve naturally beneath the uploaded config directory; absolute paths retain their literal remote meaning. Paths outside the upload are not copied, so missing remote dependencies/workdirs fail remote validation.

Forward workflow selection, `-c/--config`, `--env`, `--jobs` (as the same comma-delimited value), explicit `-p/--parallelism` (including `0`, meaning logical CPUs), and whichever of `--fail-fast`/`--no-fail-fast` was given as argument values. Keep config paths relative to the remote invocation cwd. Omitted parallelism is resolved using the member's CPU count. Never pass `--pool` or `--project` to the child. Reject remote `--log-dir` before creating a session: current pool APIs cannot return arbitrary raw log files, and decoded job events cannot reproduce arbitrary original bytes.

Run a fixed bootstrap script as the one pool exec using `argv: ["sh", "-c", <script>, <fixed-name>, ...arguments]`. The script resolves goodflows on PATH, checks its exact package version against the caller's version, and `exec`s that binary with `--json` and the forwarded arguments. Pass dynamic values through positional arguments, never shell interpolation. Bootstrap diagnostics go to stderr and do not contaminate stdout. A missing or mismatched binary fails before jobs start with a machine-readable contract: the script exits 127 when goodflows is missing and 3 on a version mismatch, after printing one fixed stderr line `goodflows-bootstrap: missing` or `goodflows-bootstrap: version <actual>`. The client recognizes only that marker line plus code (the inner goodflows never exits 3 or 127) and maps it to an `error` event naming expected/actual versions with recipe guidance, returning 1. A pool recipe must install that version plus the project's tools; the CLI never installs or upgrades it.

### 4. The member's environment owns execution

Use the prepared member environment plus config-declared settings/job/step environment. Do not copy the caller's general environment, PATH, or pool authentication key into the exec. Configured settings env and profile partition counts remain the remote binary's responsibility, including the active companion changes in this repo.

When reporting is configured, explicitly forward only the values named by its `url_env` and `token_env`, when present locally, to the remote publisher process. They are scrubbed from jobs and expressions by the existing publisher contract. Reporting defaults `url_env`/`token_env` to `GOODFLOWS_URL`/`GOODFLOWS_API_KEY` (`src/config.rs`), the same variables as pool authentication, so in the default configuration the private key is forwarded: it reaches only the remote goodflows (publisher) process environment and is removed from every job/step command environment. The scrub does not hide it from processes running as the same user that can read the parent's environment (e.g. `/proc/<ppid>/environ` on Linux); document this and recommend a separate, narrowly-scoped `token_env` for remote reporting. The pool key is forwarded only because reporting names that variable, never merely because reporting exists. No reporting block means no credential forwarding. Check request size limits before leasing; missing reporting credentials keep their existing best-effort behavior.

Automatic report publishing runs on the member and its events stream back. The inner invocation creates its own run id and report directories; the outer exec uses `collect_reports: false` and does not pretend nested reports are outer-exec reports. Git context is unavailable in the snapshot without `.git`, so existing capture yields null source fields. Remote spools survive only until member reset; this version does not provide local retry spools or promise persistence after release. Document this limitation next to remote reporting usage. A caller needing retained failed uploads uses local execution until spool retrieval is added.

### 5. Relay events, not an opaque job log

Decode base64 pool output with a per-exec sequence cursor. Reassemble stdout JSONL across arbitrary frame and UTF-8 boundaries. Preserve inner schema, workflow/environment, partition metadata, failure tails, report events, and result counts; render them through the existing output renderer without overwriting the remote default workflow name. `Output::emit` currently stamps CLI `workflow`/`environment` onto every event and the renderer sets `schema_version`; add a verbatim forwarding path in `src/output.rs` (no tagging, schema version preserved) used only for events that passed the schema check. Stderr is bounded bootstrap/runner diagnostics, not fabricated `job_output`: relay it as `remote_status` events with phase `remote_stderr`, capped at 64 KiB total per invocation (excess is truncated with a marker).

Bound incomplete event buffering (16 MiB maximum per JSONL event, including the final `summary`); reject oversized, malformed, unsupported-schema, or structurally invalid events. Verify with a test that a worst-case summary (many partitioned instances with 4 KiB tails and 64 KiB step outputs) fits the bound. The same-version check controls schema drift. Add one versioned `remote_status` event for structural pool/session/member progress, shaped `{"type":"remote_status","phase":<phase>,"pool":<slug>,"project":<slug>,"message"?:<string>}` with phases `snapshot`, `session_created`, `uploaded`, `member_ready`, `executing`, `reconnecting`, `remote_stderr`, `releasing`, and `released`; errors use the existing `error` event.

Relay decoded events to the output writer through a bounded queue (32 MiB) that is separate from the socket/heartbeat task. A stalled stdout consumer must never stop socket reads or heartbeats; if the queue overflows, fail with a structural `error`, cancel the exec, and release the session rather than dropping events or buffering without bound. Do not print command env values, raw response bodies, archive contents, or keys. JSON stdout stays JSONL. Under text mode reuse existing job/summary rendering and render remote progress concisely.

Hold the inner final summary until the pool `exit` confirms `status: exited` and the expected code (0 for successful summary, 1 for failed summary). Then emit that summary last and return the remote code. Forward an inner pre-summary error without manufacturing a summary: propagate inner exit codes 1 (configuration/runtime) and 2 (argument error) unchanged, and map recognized bootstrap failures to 1. A missing/truncated stream, missing summary for exit 0, contradictory summary/exit, outer timeout/cancellation, or transport error is a remote execution error (exit 1), never a synthesized successful workflow. A local signal received before the pool `exit` is confirmed takes precedence (130/143). Once a matching `exit` and summary are confirmed, a later signal only cuts cleanup short with an unconfirmed-cleanup warning and does not override the confirmed 0/1 code. Emit cleanup diagnostics before the held summary.

`improve-run-report` derives its text-mode rerun hint and wall time from the relayed summary. Leave that stateless renderer unchanged; in remote text mode print one line immediately before the held summary, `Remote: pool=<pool> project=<project>; append --pool <pool> to rerun remotely`, and document that the reported duration is member execution time, excluding snapshot, lease, and upload.

### 6. Resume the same exec and release the session

Keep the channel joined throughout execution. On a temporary disconnect, reconnect, rejoin, and `resume` with the last processed sequence; suppress duplicate chunks and do not re-run commands. Preserve a partially assembled JSONL record across replay. A `gap` means events may be missing, so fail explicitly and release rather than silently showing an incomplete successful run. Bound reconnect attempts to a 60-second local window and respect earlier server expiration. This window does not change the server's configured grace or lifetime.

The protocol guarantees the `exec` reply precedes that exec's first `output`/`exit`, so a slow reply on a healthy socket is not ambiguous; wait for it under a generous reply deadline. An exec push is ambiguous only when the socket drops or the channel rejoins before its reply arrives. Rejoin and recover the single running exec if the join lists it; resume that exec from sequence -1. If identity cannot be established (including an exec that already ended before the reply was received), fail and release. Never retry an ambiguous exec or create a replacement workflow execution. A lost member before execution can be replaced within the session deadline; a lost member after submission terminates the invocation.

If the upload response is lost, query session state: uploaded means wait for readiness; retrying is permitted only while no upload is confirmed, treating 409 as a reason to reconcile state rather than overwrite it. The client HTTP upload remains non-resumable. Do not retry ambiguous session creation; the server's unjoined-session expiry cleans up an unknown session.

Use bounded connect/request/readiness/bootstrap and shutdown deadlines. The outer exec omits `timeout_ms` and retains the configured server maximum (one hour by default); inner job deadlines cannot extend that limit. Apply a bounded readiness timeout after accepted upload, so repeated hydration loss cannot hang the client indefinitely. The readiness timeout is 120 seconds plus 60 seconds per started 512 MiB of expanded snapshot payload (at most 360 seconds at the 2 GiB cap), since the server hydrates the full workspace before readiness. Connect and individual REST request deadlines are 30 seconds each; the streaming upload request has no fixed total deadline but fails after 30 seconds without progress.

On Ctrl+C/SIGTERM, stop new work, send cancel for a known exec, and release via REST DELETE; return 130/143 even if transport cleanup fails. An outer SIGKILL does not reach the inner job process groups. Always end the session and reset the member after interruption, timeout, protocol failure, or normal completion; never submit another exec on that member or report cancellation as fully cleaned up merely from the outer exit. When disconnected, best-effort DELETE plus existing session expiry/reset provides recovery. Bound cleanup to 30 seconds; surface a cleanup warning if unconfirmed, preserving an already confirmed workflow exit status. The existing `cancellation()` task in `src/main.rs` handles only the first signal; remote mode must keep listening so a second SIGINT/SIGTERM during cleanup abandons the remaining cleanup, reports "cleanup unconfirmed; session expiry will reset the member", and exits immediately (130/143, or the confirmed code if one exists). Output backpressure must not prevent socket heartbeat, signal handling, or cleanup.

## Risks / Trade-offs

- Ignored dependencies or uninitialized submodules are absent from the upload -> document recipe preparation, reject submodules explicitly, and fail visibly on unavailable remote paths.
- Exact binary versions require recipe maintenance -> report expected/actual versions before job execution; upgrade recipe and CLI together.
- Replay has finite retention -> treat gaps as errors and never automatically run the workflow twice.
- Reports pending at reset cannot be replayed locally -> document the initial retention limitation; durable spool transfer is a separate capability.
- Nested command process groups outlive an outer kill until reset -> always release/reset and verify this with an opt-in real-pool cancellation test.
- Default reporting credential names forward the private pool key to the member's goodflows process -> scrub it from jobs, document same-user visibility, and recommend a separate reporting `token_env`.
- Pool transport ignores proxy variables -> document that remote runs need direct connectivity to `GOODFLOWS_URL` in this version.
- The working tree can change while archiving -> freeze a completed archive, fail detected read races, and document that users should finish edits before invoking.

## Migration Plan

1. Implement and test the client using mock HTTP/WebSocket endpoints without changing the server contract.
2. Add a pool recipe with the matching goodflows release and project toolchain; validate an opt-in smoke workflow on a development pool.
3. Release the CLI and document `GOODFLOWS_URL=... GOODFLOWS_API_KEY=... goodflows run ci --project app --pool rust-ci`.
4. Roll back by omitting `--pool` or using the previous CLI. Local TOML and server session schemas require no migration. Existing active sessions retain their current expiration/reset rules.
